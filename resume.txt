1-RaceCondition
--------------------------------------------------------------------------------

Une race condition apparaît quand plusieurs threads lisent et modifient la même donnée partagée sans coordination, et que le résultat dépend de l'ordre dans lequel ils s'entrelacen

2-Semaphore	? Combien de threads peuvent entrer en même temps ?
--------------------------------------------------------------------------------

limiter le nombre d'accès simultanés

Un Semaphore est un compteur de permis. 
 - acquire() prend un permis (ou bloque s'il n'en reste aucun)
 - release() en rend un.
 - Semaphore parking = new Semaphore(3); trois threads au plus sont dans la zone protégée en même temps.

4-CountDownLatch ? Comment attendre que N événements soient terminés ?
--------------------------------------------------------------------------------
attendre la fin de N événements

- les threads appellent countDown() pour le décrémenter
- ceux qui ont appelé await() sont bloqués jusqu'à ce qu'il atteigne 0
- CountDownLatch latch = new CountDownLatch(10);

--------------------------------------------------------------------------------
5-CyclicBarrier		? Comment faire attendre N threads les uns les autres ?
--------------------------------------------------------------------------------

Une CyclicBarrier fait attendre N threads les uns les autres : 
chacun appelle await() et reste bloqué jusqu'à ce que les N soient arrivés. 

Elle se réinitialise automatiquement : elle sert pour plusieurs étapes de suite (« cyclique »).

aucun thread ne passe à l'étape N+1 avant que le plus lent ait fini l'étape N.

CountDown à plusieurs niveau 

await() est utilisé pour attendre

7-FixedThreadPool
--------------------------------------------------------------------------------

ExecutorService executor = Executors.newFixedThreadPool(3);

.newFixedThreadPool(3) crée un pool. Les threads sont créés à la demande, jusqu'à 3,
executor.submit(tâche) dépose la tâche dans une file d'attente 
.shutdown() ferme le pool -- elle attend la fin de derniers thread 

--> shutdown obligatoire car 
- La JVM ne s'arrête que s'il ne reste que des threads daemon.
- le thread de pool sont  : non daemon 
- main non daemon

Avec N tâches bloquées, plus rien ne passe (famine).

10-deadloack
--------------------------------------------------------------------------------

les deux threads sont BLOCKEd pour toujours (chacun attend un verrou que l'autre  detient)

synchronized (from) {
synchronized (to) {
	from.withdraw(amount);
	to.deposit(amount);
   }
}

Un deadlock n'est possible que si les quatre conditions sont réunies  : Les 4 conditions de Coffman
Exclusion mutuelle ---> ressource partgé
Détention et attente --> garder le verrou sur la resource
Pas de préemption --> impossible de retirer le verrou
Attente circulaire	--> les deux point sont en circulaire


solution : casser l'un de ces conditions
1 - donner un identifiant d'ordre au objet muxtex
2 - tryLock : on retente on attendant un delais aleatoires
              on peut par exemple faire 5 retry
			  
pour refaire le retry 
on a besoin d'un variable 

ReentrantLock lock() {
	return lock;
}

dans la resource partage 	
Ceci sert à un clé pour verrouier 

* lock.unlock();
* from.lock()
